# Trust boundaries and limitations

- Default local-owner mode is a development-only workspace on loopback and is not shared-hosting authentication. Optional password mode adds operator-provisioned users, salted scrypt credentials, persisted hashed session tokens, rotation/revocation, owner/viewer membership checks on every request and workspace-scoped data/service instances. Host/origin/CSRF validation protects mutations; TLS origins use Secure/HttpOnly/SameSite=Strict host-prefixed cookies. Login and anonymous-session issuance have persisted application throttles. Never expose or proxy local-owner mode publicly. Public TLS/proxy deployment, stronger abuse controls and independent security review remain outstanding. Setup and explicit limits: `docs/ACCESS.md`.
- Money uses integer base units (2 decimals, asset `local:demo-units:2`). SQLite immediate transactions and unique payment/refund constraints serialize reservations and finalization. Final jobs cannot be replayed. The seed funding entry reconciles balances; reservation release is an internal balance operation, not an external transfer.
- Uploaded filenames are metadata, never filesystem paths. Input documents/artifacts live in the private SQLite database, with opaque upload IDs and authorized artifact routes. Unsupported inputs and size limits are enforced server-side. No arbitrary URL fetching is exposed. Documents and secrets are absent from audit logs; errors can include a local filename/field validation reason.
- Approved mandate content is immutable; approval is a distinct record. Revisions invalidate quotes and require a new owner approval. Quotes bind recipient/provider, scope hash, asset, amount and expiry. Invoice notes and model content are data and never authority.
- Verification binds job, mandate, output bytes, actual input manifest, check version, verifier, expiry and local domain. Settlement recomputes critical checks. The local report hash is an integrity checksum, not a cryptographic signature or trustless attestation. The server/database are trusted. No encryption-at-rest, formal audit, TEE, compliance certification, or document authenticity guarantee is claimed.
- Duplicate and uncertainty detection has an intentionally narrow documented definition. All invoices remain in output, including duplicates; the owner must decide their accounting treatment. Mixed currencies are never summed together.
- Both providers are demo-owned services using local parsing by default. Optional NEAR AI extraction is wired into the job UI and execution only with server opt-in and per-job consent bound to the approved mandate. Structured fields/source IDs/notes leave the machine through the fixed HTTPS endpoint. API charges are outside demo spending caps. Output is bounded, strict and independently compared to source bytes; model text cannot authorize payment. Failures do not fall back to fabricated success. Targeted real API execution passed independent checks; broader model quality and cryptographic model attestation remain unverified. Correction/crash recovery can cause another billed request; there is no upstream idempotency or distributed job lock. See `docs/NEAR_AI.md`.
- The NEAR engine separates owner, agent and verifier account/key pairs, restricts asset/domain/recipient/cap/expiry, locks asynchronous payouts/withdrawals, binds evidence to job/input/artifact, prevents quote and callback replay, and serializes payment/refund finalization. The optional testnet console implements owner wallet signing, separate role signers, code-hash checks and finalized RPC/state reconciliation. Native tests cover the engine and mocked RPC tests cover confirmation policy; WASM compilation checks the wrapper. Deployment, live-wallet and NEAR VM integration tests, storage/gas measurements, dependency review and a security review remain necessary before funded use. See `docs/NEAR_TESTNET.md`.
- Onchain funding must be an owner action. Function-call key allowances pay gas and are not spending caps; restricted keys cannot attach NEAR deposits. Never give a model a full-access owner key. The contract's funding pool also needs reviewed storage/gas economics before deployment. No invoice content belongs onchain; hashes reveal associations and are not encryption.
- No mainnet deployment, wallet funding, paid service or external transfer was performed.
- Delivery/source review and report/original downloads require the same local session and workspace ownership lookup as other private data. CSV rows are reparsed from actual bytes, with one-to-one source occurrence matching and explicit integrity/expiry states. Original text is rendered as escaped text; raw source downloads use a fixed filename and attachment/octet-stream response. Review does not authorize payment or modify delivery bytes. Exported verification metadata can still contain sensitive invoice identifiers/associations. See `docs/DELIVERY_REVIEW.md`.

## Public sample demo

The `/try-demo` visitor flow uses a separate cookie and a separate per-visitor in-memory SQLite store. It does not authenticate into owner workspaces or delegate into their API router. Only server-owned fictional fixtures, bounded local job operations and local artifact review/download are exposed. No guest file uploads, paid inference or wallet actions are supported. Host, origin, CSRF, session lifetime and resource limits are enforced. See [design and pilot limits](SAMPLE_DEMO.md) and [validation](verification/sample-demo.json).
