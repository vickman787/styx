## Start and test

For a separate installation with an existing verified contract and service configuration, a second STYX-operated ParseLab service can be provisioned using `node --env-file=data/near-testnet/app.env --import tsx scripts/near-provider-setup.ts provision <explicit-price-NEAR>`. This requests a fresh faucet-funded testnet account and installs a delivery-only function-call key. It never uses owner keys or reads the deployment administrator file. The saved private plan remains under ignored `data/near-testnet/`; only the restricted key enters app configuration. An uncertain request is reconciled against the same saved account before any further mutation. Restart the server to load verified configuration. Do not commit private files or run this to replace an existing provider.

1. Run `npm run dev`; open [the workspace](http://127.0.0.1:4173/app). The ignored `data/near-testnet/app.env` is loaded automatically when present. Keep it private.
2. Confirm **Live NEAR testnet** shows a verified deployed code and finalized block. An RPC failure is displayed as a failure, never a zero balance or successful connection.
3. Use **Connect wallet** in the header and choose Meteor Wallet or MyNearWallet for your own testnet account. Meteor's official adapter supports testnet; MyNearWallet remains available for existing connections. MyNearWallet currently displays a notice that it will sunset by the end of 2026. Your wallet account balance comes from finalized RPC data. Only testnet is supported. Wallet-account migration is separate from connecting STYX; never enter a recovery phrase into STYX.

   Wallet funds and escrow deposits are separate balances. A connected wallet remains connected during a failed escrow read; use **Refresh escrow balance** to retry balance/key reads. Reads use the official standard endpoint with a testnet-checked archival fallback. No transaction is automatically resubmitted by this read fallback. A submitted transaction still requires reconciliation before another signing attempt.
4. Fund escrow from your wallet. For a small first run, 0.05 NEAR available escrow plus the editable 0.05 NEAR storage deposit is an example starting amount. Review the combined wallet deposit before confirming. Storage credit is separate from spendable escrow; it is consumed by state growth and has no withdrawal function yet.
5. Upload your own structured JSON/CSV invoices under **Use your own invoices**. Choose local parsing to keep processing local, or NEAR AI and explicitly approve sharing invoice fields and paying API charges. Preparation verifies the actual CSV against originals without creating a demo quote, reservation or payment. Inspect the linked invoice review before proceeding. PDF/images are not supported.
6. Select your verified delivery, the 0.01 NEAR quote and an explicit cap at least that high. Review the prepared agreement and approve it in your wallet. Evidence expires; reprepare/reverify if necessary.
7. Review and submit reservation, delivery and verifier actions using the separate service roles. Then review owner release and confirm in your wallet. A paid state requires finalized transfer/callback success and matching chain evidence.
8. Inspect the real transaction links. Refund returns a reservation to internal available escrow; withdrawal separately transfers available escrow back to its owner. Reconcile pending requests before retrying.

The source picker and agreement API accept only owner-uploaded invoice evidence; sample jobs cannot be selected. Workspace deliveries and Activity exclude local demo jobs, and startup no longer seeds sample jobs. Existing practice records remain available through Local testing and its explicit demo routes. They are not converted into NEAR. The persistent payment-mode footer notice has been removed; the header retains the small NEAR testnet badge.

## Verification and remaining limits

The public RPC confirmed network, contract code/domain/version and the contract account balance. The browser test checks live chain data, uploads an acceptance invoice, verifies the unchanged demo ledger, checks desktop/mobile widths and accessibility, and cancels its local acceptance evidence afterward. It does not log in to a wallet or sign owner transactions.

The VM executes the actual WASM and tests real sandbox receipts/transfers, successful withdrawal, rejected private callbacks, repeated payout rejection, insufficient-storage rollback, and failed payout recovery. This is a bounded smoke, not a contract audit or large-state gas/storage certification. The native engine's 15 tests also pass. SDK native host tests remain blocked by the Windows compiler environment; actual WASM VM execution is now available through Ubuntu.

Owner Meteor signing, funding and the full approval/reserve/deliver/attest/release walkthrough have passed with actual finalized testnet receipts. Each agreement now shows progress and the next step; Paid agreements offer Full payment receipt, Download invoice CSV and Print / save receipt PDF. Print opens the browser dialog; choose Save as PDF to export only the selected receipt. It records reconciliation timestamps, not invented block timestamps, and separates unused allocation from a refund transfer.

Unused storage credit withdrawal, state cleanup/scalability, independent review, the second provider's owner-paid acceptance and failure-path operator acceptance remain open. Real AI is configured and one actual synthetic inference passed all six independent checks; see [AI setup and limits](NEAR_AI.md) and [report](verification/ai-live-check.json).
